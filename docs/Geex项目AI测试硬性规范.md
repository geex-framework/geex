# Geex 项目 AI 测试硬性规范

版本: v1.0 | 制定日期: 2026-09-27

适用范围: 基于 Geex 开发的项目, 包括业务模块及其使用的框架/扩展能力. 具体模块/入口/依赖/部署方式以各项目实际情况及已确认交付范围为准.

适用环节: AI 编码/开发自测/模块验收/独立 AI 全量收口/人工复验交接.

交付顺序: **AI 开发并同步编写测试 → AI 执行测试与修复 → 独立 AI 全量收口完全通过 → 人工复验通过 → 按上线流程发布**.

本文件是执行规范, 不代表测试工具/证据采集/自动门禁已实现, 也不代表项目已通过运行验收.

## 1. 约束/范围与判定依据

### 1.1 约束用语

- **必须/禁止**: 硬性要求, AI 不得自行忽略.
- **应**: 默认采用; 不适用时必须在测试计划中说明依据和替代验证方式.
- **可**: 按风险选用, 不自动成为所有任务的必测项.
- **完全通过**: 仅指第 11 节规定的已确认完整范围内的全量收口结论.

每次改动必须识别影响范围/完成对应验证/保存证据, 不要求每次小改动执行全项目测试. 全量收口必须覆盖完整的已确认交付范围.

### 1.2 业务依据及冲突处理

预期结果按以下优先级确定:

1. 用户/业务负责人已确认的业务规则/验收条件/变更记录.
2. 已确认的接口契约/页面交互/设计基准/计算口径.
3. 项目现行业务流程文档中的流程/入口/依赖/实现边界.
4. 当前代码/数据库结构/实际运行现象, 用于定位实现和发现差异.

已弃用或明确排除的需求文档不得作为测试依据. 旧版本源码可解释迁移差异, 未经确认的旧行为不能自动成为验收标准.

流程文档是静态现状描述, 其中的计算/限制/疑点不自动成为正确规则. 实现与已确认规则冲突时记录缺陷; 关键规则未确认时列出证据和问题, 将依赖项标为 `BLOCKED`.

禁止按实际输出反向修改预期/复制生产实现作为唯一计算依据/降低断言/隐藏差异/跳过用例以获得通过. 合法规则变更必须有确认依据, 同步更新规则/用例/基线/影响范围.

### 1.3 范围冻结与可追溯性

执行前必须建立或更新覆盖矩阵:

`业务流程/规则 → 用例 → 测试代码或人工步骤 → 本次执行 → 本次证据 → 缺陷 → 修复与复测`

| 必填字段 | 要求 |
| --- | --- |
| 流程/规则 ID | 稳定唯一, 注明模块/规则来源/确认状态 |
| 场景 | 角色/前置条件/状态/输入/操作/预期/影响数据 |
| 用例与实例 ID | `caseId` 标识用例, `instanceId` 标识参数/角色/浏览器/视口组合, 均稳定唯一; 重试不新建计划实例 |
| 测试方式 | 单元/组件/接口/ApiFlow/E2E/数据/视觉等 |
| 实现定位 | 测试文件及用例名, 或可重复的操作步骤 |
| 执行范围 | `applicability`/`requiredStages`/原因/确认依据, 区分本次必测/后续必测/经确认不适用 |
| 执行与证据 | runId/结果/证据完整性/证据路径/缺陷与复测链接 |

必须结合流程/路由/接口/状态/角色/数据关系识别范围, 重新核对已有用例对真实业务的覆盖, 不能仅以测试文件列表充当需求清单.

禁止失败后静默删除/降级/缩小已确认范围. 不适用条目保留登记/原因/确认依据, 不得记为已执行的 `PASS`.

全覆盖指已确认范围内流程/规则/必测场景完整, 不等于源代码 100% 行覆盖率, 也不证明未知缺陷不存在.

### 1.4 适用性与阶段范围

适用性是范围属性, 与第 8 节执行状态分开记录:

| 范围属性 | 含义与处理 |
| --- | --- |
| `applicability = APPLICABLE` | 纳入验证范围; 按 `requiredStages` 确定应执行阶段 |
| `applicability = NOT_APPLICABLE` | 已确认不适用; 必须保留原因和确认依据, 不生成运行状态, 不计为 `PASS` |
| `requiredStages` | 该实例必须执行的阶段列表; 后置项保留计划, 不计入当前阶段结果及分母 |

未获确认的不适用申请不得移出必测清单; 依赖确认而无法验证的项记为 `BLOCKED`. 环境未就绪/工具缺失/执行失败/来不及测试均不是不适用理由.

按交付物实际能力确定验证层: 有 UI 的应用覆盖界面/后端/数据及真实浏览器核心链; 无 UI 的服务或框架/扩展库可登记界面项不适用, 但必须经实际部署的服务或真实宿主/消费者验证公开能力及适用持久化结果. 无持久化等其他能力按同一原则登记, 不得因此免除存在的能力或最终应用集成验证.

冻结的本阶段必测清单以唯一 `instanceId` 为单位. 分母包含其中的 `FAIL`/`BLOCKED`/`NOT_RUN`, 仅排除经确认不适用和不属于本阶段的项; 重试次数另计. 验收通过数只计当前有效结果为 `PASS` 且证据 `COMPLETE` 的实例, 并须满足版本/缺陷等门禁. 分母为 0 不得报告 100% 或测试通过. 全量收口包含完整交付范围的全部适用必测实例.

## 2. 执行阶段与职责

### 2.1 阶段要求

| 阶段 | 必须完成 | 并发/性能/持续稳定性 |
| --- | --- | --- |
| 编码前 | 确认规则/影响范围/验收条件, 列出正常/异常/权限/边界场景 | 可登记风险和计划, 默认不执行专项 |
| 开发过程 | 同步完成必要测试, 验证当前可运行层并采集证据 | 默认排除, 用户明确指定时执行 |
| 模块/流程验收 | 本模块三层验证/完整业务链/关联回归/视觉检查/证据审计 | 默认排除, 登记为全量收口必测项 |
| 独立 AI 全量收口 | 独立审查完整范围, 在固定版本和目标环境完成第 11 节门禁 | 必须执行适用专项 |
| 人工复验交接 | 同一候选版本/完整证据/覆盖矩阵/复验入口 | 交付 AI 全量记录, 按人工复验安排处理 |

单用户重复点击/顺序重复请求/超时重试/刷新回退导致的重复提交属于日常功能与异常测试, 不得因专项后置而省略. 并行压测/多用户竞争/容量/长时间负载按上述阶段执行.

### 2.2 角色与独立验收

- **开发 AI**: 实现及必要测试/自测/原始证据/缺陷定位修复/回归.
- **独立验收 AI**: 独立核对业务依据/覆盖矩阵/预期/运行结果/证据, 补足遗漏并形成结论.
- **用户/业务负责人**: 确认业务歧义/交付范围/例外/专项目标, 完成人工复验和上线决定.

独立验收必须使用未参与本次被验收实现/预期/测试编写或修改的单独任务或 Agent 上下文, 不要求不同模型. 可以复用已审查的测试和采集工具, 但必须自行核对预期依据并实际执行本次验收, 不得以开发 AI 报告或结论替代验收证据. 执行记录须标识开发/修复/验收上下文及其职责.

验收 AI 可以提出问题/补充场景建议/协调修复. 一旦直接修改被测实现/预期/测试, 即参与修复, 修复后的最终验收必须交由未参与该修复且满足上述独立要求的新上下文完成. 原上下文可提供交接资料, 不得以自身修复说明或自测替代独立验收.

常规测试/修复/证据保存按开发任务授权执行, 无需逐项重复申请. 业务歧义/范围缩减/验收标准改变/上线行为不得由 AI 自行决定.

## 3. 三层验证与测试方式

三层验证相互核对**界面行为/后端规则/持久化及业务结果**, 各层按第 1.4 节登记适用性. 不同方式可跨层提供证据, 同一执行不得重复命名以增加覆盖数量.

### 3.1 前端与浏览器

| 方式 | 验证内容与要求 |
| --- | --- |
| 单元/组件 | 格式转换/状态计算/组件行为/表单校验; 独立业务行为或复杂状态按风险编写 |
| 页面集成 | 组件协作/表单联动/查询参数/错误提示/状态切换; 声明 Mock 边界, 不替代真实联调 |
| Playwright E2E | 真实页面操作经后端写入并呈现结果; 核心业务链必须稳定可重复, 覆盖真实角色与权限 |
| 布局断言 | 遮挡/裁切/溢出/错位/不可点击/滚动/固定区域; 布局及关键交互变更必须覆盖 |
| 视觉回归 | 稳定关键页面建立核准基线, 按第 7 节对比页面/组件/关键区域 |
| AI 实际截图检查 | 必须读取本次截图, 记录布局/内容呈现/可读性的具体观察与结论 |
| 兼容性与可访问性 | 按支持矩阵及涉及控件检查浏览器/视口/缩放/焦点/关键键盘路径 |

E2E 是测试方式, Playwright 是工具, 两者不能重复算作独立保障. 页面打开/按钮可点/成功提示/截图存在均不能单独证明业务成功; 必须核对后端及持久化结果, 确认刷新或重新查询后仍正确.

### 3.2 后端与接口

| 方式 | 验证内容与要求 |
| --- | --- |
| 领域/单元 | 计算/日期/额度/状态转换/校验/边界/分支; 随规则同步编写, 预期明确 |
| 单接口 | 入参/输出/错误码/认证/授权/字段/边界; 不只断言 HTTP 200, GraphQL 必须检查 errors 与业务结果 |
| 接口集成 | API 与数据库/领域服务/框架/文件的协作, 检查事务和副作用, 声明真实及替身依赖 |
| ApiFlow | 经公开接口完成创建/提交/审核/执行/撤销等实际状态链, 逐步断言, 覆盖失败分支及数据变化 |
| 接口契约 | GraphQL Schema/操作文档/输入输出/枚举/空值约定一致; 接口或生成客户端变更必须验证 |
| 后台任务/事件 | 定时处理/异步任务/事件副作用/失败恢复; 存在对应能力时必测, 等待有界且可观测 |

ApiFlow 的目标动作必须通过被验收的公开业务接口完成. 领域对象直调只能证明领域行为, 不能证明页面调用的公共接口正确. Fixture/管理接口仅可准备非测试目标的前置数据, 必须声明方式; 不得借准备步骤绕过本应验证的登录/授权/审批/状态变化.

进程内宿主测试不能证明实际部署的 TLS/代理/路由/认证配置/网络/进程边界正确. 全量收口必须补充真实部署的服务/宿主集成验证, 有 UI 的交付物还须浏览器验证.

### 3.3 数据与业务结果

| 方式 | 必须核对 |
| --- | --- |
| 独立计算 | 按已确认口径独立给出输入与预期, 核对数量/金额/余额/占用/比例/汇总/舍入等业务计算 |
| 持久化 | 保存前后字段/状态/关联/数量/修改范围; 重新查询或重启后的必要保留 |
| 多层一致性 | 页面/接口/数据库/统计/导出一致, 更新时延有明确约定 |
| 失败与回滚 | 校验失败/权限拒绝/异常/取消不留下不应发生的写入或重复副作用 |
| 数据生命周期 | 新建/修改/作废/删除/执行/取消对引用/余额/汇总的影响 |
| 导入导出与附件 | 文件实际生成且可读, 内容/权限正确, 失败行/重复数据/文件清理符合约定 |
| 迁移与升级 | 数据/结构/配置迁移前后的完整性/兼容性/关联/汇总/可恢复性 |

独立预期可用人工可核算样本/已确认公式的单独实现/已确认样本文件, 禁止调用被测函数生成 expected 再与其实际结果比较.

数据库查询或诊断接口只能作用于授权测试环境; 不得先手工修正数据再宣称流程通过.

### 3.4 横向验证

必须按影响范围完成构建/类型与静态检查/权限与数据隔离/错误恢复/依赖及配置兼容性验证.

每次测试前必须成功构建当前待测项目及必要依赖, 确认构建的代码/配置/产物与本次测试一致. 测试命令已包含构建时不重复构建; 使用跳过构建选项须关联本次成功构建记录. 构建失败立即停止依赖测试, 保留失败证据, 受阻项记为 `BLOCKED`, 禁止使用旧产物验证当前代码. 无构建步骤的项目须依据项目说明登记; 无法确认时先向用户确认.

安全场景应覆盖适用的未登录/会话失效/角色越权/直接调用受限接口/修改他人数据 ID/文件访问/敏感数据暴露. 公司/组织/租户隔离以已确认权限模型为准, 不得假定存在或不存在.

覆盖率仅用于发现遗漏, 不单独构成验收通过条件. 性质/模糊/变异测试可强化高风险规则, 未明确要求时不作为普通变更的固定负担.

## 4. 项目业务覆盖要求

### 4.1 按实际能力建立流程清单

各项目必须根据现行业务流程和已确认交付范围建立完整清单, 将下列适用类别拆成用例并随交付范围更新. 本表不代表已经通过, 也不假定项目已启用所有 Geex 扩展.

| 范围 | 必须形成的验证链 |
| --- | --- |
| 身份与基础资料 | 登录/会话 → 角色/权限/对象归属 → 基础资料维护 → 查询/关联使用/限制 |
| 核心业务流程 | 前置资料 → 业务对象创建 → 提交/审核等实际状态链 → 执行/取消 → 最终业务结果 |
| 关联与资源约束 | 上下游关联 → 数量/额度等约束 → 修改/删除/撤销 → 引用/状态/余额核对 |
| 查询与分析 | 数据来源 → 筛选/查询/统计刷新 → 独立汇总 → 报表/导出一致性 |
| 异步与外部协作 | 任务/事件/通知或外部调用 → 可观测完成条件 → 失败/重试/恢复 → 持久化及副作用核对 |
| 通用与共享能力 | 搜索/分页/排序/导入导出/附件/枚举/校验提示/公共审批/异常恢复/权限隔离及跨模块使用 |

相似名称的实体/计划与实际记录/状态标记与实际操作/不同关联关系, 必须按已确认语义分别验证, 不能推断自动衔接或等价.

流程文档或代码检查中发现的接口接线/统计占位或口径/关联更新/提前副作用等疑点必须登记专项验证. 静态疑点不等于运行故障, 未运行也不等于已解决.

### 4.2 每条流程的场景维度

适用范围内, 每条业务链必须覆盖:

1. 正常主链: 前置资料/逐步输入/状态转移/最终结果.
2. 分支与逆向: 驳回/取消/撤销/修改/作废/删除/恢复, 以实际支持或已确认应支持的动作为准.
3. 边界: 空值/零/负数/极值/长度/日期边界/金额精度/币种/舍入.
4. 权限与状态: 角色/归属/未登录或过期/禁止状态下直接调用接口.
5. 顺序重复与异常: 重复提交/超时重试/刷新回退/断网或失败反馈/副作用.
6. 关联变化: 上游修改/删除限制/下游引用/汇总更新.
7. 呈现与数据: 刷新后显示/独立持久化核对/报表及导出一致性.

不存在的分支登记为不适用, 不得虚构规则凑用例. 适用异常用例应同时断言正确拒绝和未产生不应发生的数据变化.

## 5. 编码时同步生成测试

### 5.1 同步开发要求

| 开发节点 | 必须同步完成 |
| --- | --- |
| 规则确定 | 验收条件/样本输入/独立预期, 登记歧义 |
| 领域实现 | 规则/边界/失败分支的必要测试 |
| API 实现 | 接口/集成/契约测试, 覆盖授权及副作用 |
| 业务链打通 | ApiFlow, 核对真实接口顺序和最终数据 |
| 页面可联调 | 关键 Playwright E2E/布局/适用视觉验证 |
| 模块交付 | 补齐跨模块/异常/权限/数据核对, 提交证据及结果 |
| 缺陷修复 | 保留失败复现, 补充防复发回归, 执行影响范围验证 |

禁止默认将所有测试延后至开发完成或验收时编写. 暂不可运行的用例可先设计/实现, 但保持 `NOT_RUN` 或如实标为 `BLOCKED`, 写明后续执行条件.

测试应验证有用户或业务意义的行为. 文字/简单样式变更可复用已有测试并做针对性浏览器/视觉检查, 不机械新增与实现同构的单元测试.

### 5.2 影响分析与维护

每次变更必须识别受影响的规则/接口/页面/角色/数据/报表/公共组件并选择回归范围. 公共审批/权限/计算/共享表单/框架/数据库变更应扩展至所有相关流程.

测试代码/Fixture/预期数据/快照/覆盖矩阵必须随业务同步维护. 测试辅助逻辑故障也必须记录修复, 不能计为产品通过.

**已生成测试 ≠ 已执行; 已执行 ≠ 已通过; 执行通过 ≠ 验收通过.**

### 5.3 文档维护边界

长期文档按公共能力/模块/工具职责组织. 功能文档维护当前 API/配置/行为与兼容性约束, 通用测试编写指南只说明用例设计/断言/隔离/辅助代码与执行脚本的写法. 具体测试入口/依赖准备/验证边界/证据定位由所属模块验证文档或脚本说明维护. 功能契约由所属文档维护, 模块验证文档引用契约和测试代码, 不重复罗列每次修复的实现细节和断言.

普通修复不要求新增或修改测试说明文档. 通用编写指南仅在编写方法变化时更新; 测试入口/环境依赖/参数/长期验证方式/工具能力或证据约定变化时, 更新所属模块验证文档或脚本说明. 新增测试用例本身不构成新建专项文档的理由. 一次任务涉及多个模块时, 长期契约分别归入所属模块, 不以补丁/任务名称建立永久功能或测试目录.

本次影响范围/冻结覆盖矩阵/执行结果/缺陷与阻塞随运行证据保存, 变更经过由提交记录或 PR 说明承载. 长期流程覆盖矩阵按模块维护, 本次冻结快照引用其依据. 必要的测试代码/Fixture/预期数据仍按第 5.1/5.2 节维护, 文档精简不免除实际验证和证据要求.

## 6. 环境/版本/数据与可重复性

### 6.1 执行环境

每次必须记录适用环境信息, 不适用项关联第 1.4 节依据:

- 主仓库及实际参与构建的框架/依赖仓库提交和工作区状态; 未提交差异及相关新增文件内容或可校验归档, 仅 HEAD 不足以标识脏工作区.
- 测试版本/依赖锁文件摘要/运行时与包管理器/数据库/浏览器版本.
- 前后端/数据库/缓存及适用服务的部署身份/地址别名/脱敏配置摘要.
- 构建产物身份/非敏感配置摘要/测试时间/时区/视口/语言等参数.

以 `baselineId` 关联本次源码/依赖/测试/产物/配置/数据集及预先声明的环境矩阵. 该标识必须对应可核查的内容, 不能仅用同名版本标签证明一致. 生产候选构建和测试必须指向同一冻结基线.

敏感配置使用版本标识或受控引用, 不保存明文密钥, 不以公开摘要泄露低熵密码等秘密.

开发自测可用开发环境; 全量收口必须包含生产构建及接近目标部署方式的验证. 进程内/开发服务/候选部署结论必须区分, 不得互相冒充.

禁止默认用生产业务数据进行写入/删除/压力/故障注入测试. 测试账号/数据库/对象必须有明确隔离边界.

### 6.2 测试数据

- 使用可重复 Fixture/种子数据及可检索的本次测试标识, 记录创建/使用/清理的对象 ID 和前后状态.
- 权限用例使用对应普通账号, 不得全部以超级管理员替代.
- 金额/日期固定必要输入, 记录系统时间/业务日期; 随机数据记录种子.
- 声明 Mock/Stub/预置数据/人工准备及其未验证的真实依赖.
- 先保存断言与证据再清理数据, 记录中断残留及清理办法; 清理仅限本次授权对象或明确隔离环境.

外部服务不可用时可用替身支持局部开发. 已确认范围内的真实联调仍标为 `BLOCKED` 或 `NOT_RUN`, 不得以替身通过替代全量通过.

### 6.3 重试与不稳定用例

等待应基于可观测业务条件并有合理上限. 禁止无限重试/扩大超时/固定长等待/只保留最终成功来掩盖失败.

保留全部尝试/重试原因/最终处理. 未解释或未修复的偶发失败仍是待解决问题, 重跑成功不消除原失败, 不得据此宣称完全通过.

修复复测与原失败分开保存, 以缺陷 ID 关联. 清缓存/重启服务/重建数据等条件变化必须记录.

## 7. 页面布局与视觉质量

### 7.1 三种方式共同验证

关键页面采用**布局断言 + 视觉对比 + AI 实际截图检查**. 截图存在不等于已检查, 图片相似不证明可操作. 此项属于日常前端要求, 不得随性能测试后置.

| 类别 | 必测内容 |
| --- | --- |
| 几何与交互 | 控件可见可操作/按钮无遮挡/文本无异常裁切/弹窗及抽屉位置与滚动 |
| 页面结构 | 导航展开收起/固定列及表头/分页/底部按钮/横纵滚动/下拉浮层层级 |
| 内容压力 | 长名称/长数字/长中英文/完整与空数据/多条错误/适用大列表 |
| 页面状态 | 首次加载/加载中/成功/空态/校验或请求失败/无权限/会话失效 |
| 显示条件 | 已确认浏览器/最小及常用桌面视口/适用缩放与响应式模式 |
| 可理解性 | 标签与值对应/金额单位和日期清楚/错误可读/结果明确/关键键盘路径可用 |

执行前必须列明浏览器/视口/适用页面的支持矩阵; 单一配置不能代表所有浏览器或移动端.

### 7.2 基准与差异处理

基线必须先对照已确认设计或验收条件检查. 无基线时先做布局断言及截图检查, 经核准建立首版; 更新须有设计/功能变更依据并独立复核, 禁止失败后批量接受截图.

必须固定或记录浏览器/系统/字体/视口/语言/缩放/数据/必要时间. 动态区域可最小范围稳定化或遮罩并记录原因和区域, 禁止遮罩主业务或异常位置.

差异阈值须预先配置并说明依据, 不得失败后单纯放宽. 阈值内仍存在遮挡/裁切等实际问题时判失败.

成功保存关键状态截图及观察结论; 视觉失败保存基准图/实际图/差异图/断言/问题位置. AI 必须关联截图和检查点说明实际观察, 不能只写 "视觉正常".

## 8. 结果状态/缺陷分级与关闭

### 8.1 用例状态

| 状态 | 定义与处理 |
| --- | --- |
| `PASS` | 本次实际执行且预定断言全部通过; 证据完整后才计入验收通过 |
| `FAIL` | 实际与预期不符; 关联缺陷/原始证据/影响范围/修复复测 |
| `BLOCKED` | 前置故障/环境/数据/权限/规则不明导致无法完成; 记录原因/依赖/解除条件, 不计通过 |
| `NOT_RUN` | 应执行而未执行, 或记录不足以证明完成; 记录原因和后续安排, 不计通过 |

负向用例正确拒绝且副作用符合预期可为 `PASS`. 中断时已完成项保留实际结果, 受阻未完成项为 `BLOCKED`, 未开始项为 `NOT_RUN`; 不得用进程退出码代替逐项状态.

每项另记 `evidenceStatus = COMPLETE / INCOMPLETE`. 运行器 `PASS` 但缺规定证据时, 记录 "PASS, 证据不完整", 不计验收通过; 补写说明不能代替缺失运行证据.

本节状态只用于本阶段必测实例. 未启动项没有实际执行 ID/起止时间, 尝试列表为空; 已启动但中断的项保留真实尝试及停止位置. 不适用和后置项保留在范围记录, 不伪装成 `PASS` 或当前阶段的 `NOT_RUN`.

### 8.2 缺陷严重程度

严重程度属于缺陷, 不替代用例状态:

| 等级 | 判定依据与例子 |
| --- | --- |
| `BLOCKER` | 核心业务大范围中断/严重安全后果/不可恢复数据损害, 如公共流程瘫痪/严重数据损坏/越权泄露 |
| `MAJOR` | 重要功能/局部流程/关键数据或计算/必要交互错误, 如重要保存失败/计算错误/关键按钮遮挡 |
| `MINOR` | 不影响流程/权限/数据正确性/关键含义的轻微问题, 如间距/对齐/文案瑕疵 |

按业务影响/范围/数据风险定级, 不按修复耗时/代码量/通过率需要. 样式导致关键按钮被遮挡须按后果评为 `MAJOR` 或更高.

`BLOCKED` 不等于 `BLOCKER`: 接口故障的实际失败用例为 `FAIL`, 依赖它而未完成的后续项为 `BLOCKED`, 关联同一缺陷, 不重复计为新缺陷.

### 8.3 缺陷关闭

每个缺陷必须有唯一 ID/描述/预期与实际/严重程度及理由/复现步骤/受影响版本和场景/原失败证据/原因/修复版本/回归用例/复测及关联回归结果.

代码修复不等于关闭. 必须有修复版本的有效复测证据, 并确认相关流程未被破坏. 重复缺陷/误报/合法规则变更保留处置依据与关联记录, 不得删除失败历史.

暂缓 `MINOR` 不得将对应失败改为 `PASS`; 任何等级未解决缺陷均不满足全量收口完全通过.

## 9. 所有测试证据必须落盘

### 9.1 总原则

**每项测试必须追溯到本次真实执行及完整证据. 成功/失败/阻塞/未执行均须记录, 只有实际执行的步骤才有运行结论.**

执行中以自动采集为主, AI 观察在检查当时记录. 禁止凭回忆补造请求/响应/截图/日志/时间/结果/数据, 禁止以代码阅读/旧截图/旧报告替代本次运行.

阻塞/未执行项保存计划/停止位置/原因/已有诊断, 不要求或伪造未执行页面的运行截图. 崩溃/超时/中止保留部分证据并标记缺口.

### 9.2 各类测试最低证据

| 类型 | 成功与失败均需保存 | 失败/异常额外保存 |
| --- | --- | --- |
| 构建/静态检查 | 命令/目录/版本/起止时间/退出码/原始输出/结论 | 诊断与失败定位 |
| 单元/组件 | 逐用例可定位的机器报告及日志, 重要计算的输入/预期/实际 | 断言/堆栈/参数化实例/复现输入 |
| API/契约/集成 | 脱敏请求响应/身份与角色别名/逐项断言/业务 ID/必要前后状态 | 完整错误结构/关联服务日志/异常副作用 |
| ApiFlow | 每步请求响应/断言/状态变化/步骤关联 ID/最终数据及核对 | 原失败步骤/已完成步骤/受阻后续/数据残留 |
| Playwright E2E | 完整 Trace/关键步骤截图/报告/断言/控制台错误及失败请求记录 | 失败截图/网络与服务日志/按需视频 |
| 视觉与布局 | 页面状态及视口元数据/布局断言/关键截图/基准版本/AI 检查记录 | 基准图/实际图/差异图/异常位置/交互影响 |
| 数据/报表/文件 | 独立预期及口径/实际查询或文件/差异核对/业务 ID/时间点 | 差异明细/异常记录/关联上游步骤 |
| 并发/性能/稳定性 | 场景与工具配置/负载模型/数据规模/预设阈值/原始结果/系统指标/汇总 | 失败请求/竞争后数据/资源异常/时间关联 |
| 部署/升级/恢复 | 产物身份/脱敏配置/日志/前后核对/冒烟 | 失败点/恢复过程/数据差异/当前可用性 |

无控制台错误或失败请求时, 也须保存 "已采集, 数量为 0" 的结构化记录. 负向用例的预期拒绝/错误须标注并与意外异常区分, 既不机械报缺陷, 也不全局忽略错误.

单元测试可共享报告, 不要求逐例目录或截图, 但必须可检索用例 ID/参数/结果. ApiFlow/E2E/数据核对须保留可复现关键步骤的细节.

Trace/请求日志按第 9.5 节处理. 性能测量须明确采集配置及开销, 不得把重型浏览器录制耗时当作无录制性能.

### 9.3 目录和命名

目录按规则文档/测试工具与代码/单次运行证据分开组织. 默认结构如下; 已确认的等价布局或制品存储必须保留同等信息/稳定定位/校验能力, 通过入口和索引映射, 不为统一路径搬迁或重命名历史证据:

```text
README.md                         # 项目入口/公共能力与模块文档导航
docs/
  Geex项目AI测试硬性规范.md         # 通用测试与证据规则
  ...公共能力文档...               # 当前契约/用法/约束
framework_modules/<module>/ 或 frontend_libs/<package>/
  README.md                       # 模块契约/配置/使用方式
  TESTING.md                      # 按需维护环境准备/人工验证步骤
scripts/testing/
  README.md                       # 测试代码与执行脚本的通用写法
  ...现有执行入口...
  schemas/                        # 机器记录格式定义
  templates/                      # 记录及报告模板
tests/ 或各技术栈现有测试目录/     # 测试/Fixture/核准基线
.test-evidence/<runId>/
  report.md                       # 本次报告, 引用机器结果及原始观察
  handoff.md                      # 长任务按需保存本次续接说明
  manifest.json                   # 执行身份/范围/版本/环境/结论
  cases.jsonl                     # 逐用例及实例结果
  artifacts.jsonl                 # 证据索引/大小/SHA-256/关联用例
  scope/                          # 范围快照及依据
    cases.jsonl                   # 冻结计划实例/适用性/阶段/规则及预期引用
  environment/                    # 版本/脱敏配置/差异/产物身份
  runner/<invocationId>/           # 每次运行器调用的命令/日志/原始报告
  api/<instanceId>/<attemptId>/    # 请求/响应/断言/步骤/数据状态
  browser/<instanceId>/<attemptId>/ # Trace/截图/错误/适用视频
  data/<instanceId>/<attemptId>/   # 预期/查询/差异/导入导出样本
  visual/<instanceId>/<attemptId>/ # 基准/实际/差异/检查记录
  nonfunctional/                  # 并发/性能/稳定性, 仅适用阶段
  deployment/                     # 部署/升级/重启/恢复
  defects/                        # 缺陷及修复复测关联
  gate-result.json                # 证据审计及门禁结果
```

目录约定不表示工具或采集能力已实现. 保留技术栈现有测试目录及核准基线位置, 不为统一名称搬迁代码. 证据分类目录按实际需要创建, 不用空目录或空文件冒充证据.

**入口与续接.** 根 README 提供规范/功能文档/测试编写指南的稳定入口. scripts/testing/README.md 只说明通用测试写法, 不登记具体功能的测试范围/命令/结果. 具体执行入口和环境准备由脚本说明或所属 TESTING.md 维护, 不要求另建集中测试文档目录. 入口只在导航变化时更新, 不逐次登记修改和运行结论. 本次范围/台账/证据通过运行包的 report.md/manifest.json 定位, 模块验证文档或脚本说明提供访问方式. 已有 AI 工作指引引用相应入口, 不复制整份规范. 长任务需要跨上下文续接时, 在本次运行目录按需保存 handoff.md, 记录 scopeId/当前基线/相关 runId/阻塞/下一步/更新时间及证据引用, 随本次证据归档. 后续续接在新运行目录记录并引用先前 runId, 不回写已归档目录. 续接时先核对当前基线和真实记录, 交接说明不能替代运行结果或授权, 也不能以最近运行推断最近验收通过.

**报告与证据同包.** 每个 run 的 report.md 与机器记录及证据统一归档, 外部制品须有交接方可访问的稳定引用. 报告中的状态/数量/门禁结论必须由本次机器记录生成, AI 或人工观察保留原始出处. 文档区仅保存索引或同源生成的报告视图, 不手工维护第二份运行结论. 证据使用相对运行根目录的路径或稳定制品引用, 不以执行机绝对路径作为唯一交付地址.

**命名.** runId 必须唯一, 推荐 UTC 紧凑时间加随机后缀, 如 `20260927T081530Z-a1b2c3d4`; 创建目录时检查冲突, 不只依靠秒级时间. 阶段/模块/版本以 manifest.json 中的元数据为准. 新机器产物采用固定英文名, 用于路径的 ID 保持短且符合目标文件系统规则; 不直接拼入用例标题或完整参数. 若逻辑 ID 不适合路径, 必须记录它与唯一目录键的映射, 禁止静默截断导致碰撞. 现有中文文档名可保留. 机器记录时间使用带时区 ISO 8601, 展示可用 `yyyy-MM-dd HH:mm:ss` 并注明时区.

**并行写入.** 独立运行使用不同 runId. 同一 run 内, 各执行单元写独立文件, 由单一汇总器校验后生成统一 manifest/cases/artifacts/gate-result, 禁止多个执行单元并发追加同一结果文件. invocationId 标识本 run 内一次运行器调用, 用于关联命令/输出及产生的尝试, 不替代 instanceId/attemptId/executionId. 采集并行不改变第 2.1 节业务并发测试的阶段安排.

**输出隔离与归档.** 每次运行器调用必须使用本次专属输出目录, 默认 runner/<invocationId>/; 工具自己的清理动作只能作用于该目录, 不得指向历史证据根目录/其他调用目录/已归档目录. 原执行/重试/复测和不同尝试的输出均须可区分, 不共享会覆盖内容的 latest 结果目录. 归档前核对证据引用与完整性, 归档后禁止后续执行覆盖; 崩溃或中断仍保留已产生证据, 保留和清理按第 9.5 节处理.

### 9.4 机器记录最小字段

| 文件 | 必须记录 |
| --- | --- |
| `manifest.json` | schemaVersion/schemaRef/runId/stage/baselineId/起止时间/执行者与验收者及上下文职责/scopeId/完整阶段范围引用与摘要/plannedInstanceIds/各仓库版本及工作区状态/测试代码与产物身份/环境/依赖/配置引用/构建与命令记录(含 invocationId/输出目录)/数据集引用/计划实例及逐状态数量/证据完整性/报告及门禁结果引用 |
| `scope/cases.jsonl` | scopeId/caseId/instanceId/flowId/ruleIds/测试类型/角色/场景/参数/浏览器与视口/前置条件/操作与预期依据/实现定位/applicability/requiredStages/applicabilityReason/confirmationRef/evidenceRequirements |
| `cases.jsonl` | runId/instanceId/scopeRef/status/evidenceStatus/断言摘要/artifactIds/缺陷与阻塞引用/finalExecutionId/attempts; 用例及场景信息通过 scopeRef 关联冻结范围 |
| `attempts` 内每次真实尝试 | executionId/attemptId/baselineId/关联 invocationId(由运行器产生时)/原始运行器状态/实际起止时间/停止位置/status/evidenceStatus/断言摘要/artifactIds/缺陷与阻塞引用/重试或复测来源 |
| `artifacts.jsonl` | artifactId/runId/关联层级/类别/相对路径或制品引用/产生时间/大小/SHA-256/媒体类型/脱敏说明; 实例级附 instanceId, 尝试级另附 executionId/attemptId |
| `gate-result.json` | schemaRef/检查范围及 baselineId/纳入的 runIds/逐实例有效结果与执行引用/逐门禁 ID/判定/计数/失败或不适用原因/确认依据/关联证据/检查器身份/起止时间/工具退出码 |

应执行实例必须预先登记, 不得从成功输出反推范围. `scope/cases.jsonl` 按 `instanceId` 唯一; 每个 run 在执行前声明 `plannedInstanceIds`, 为冻结阶段清单的全部或明确子集. `cases.jsonl` 每行唯一对应本次计划内的 `(runId, instanceId)`, 不适用/后置/其他批次项不生成本批次结果, 但保留完整范围登记. 参数和支持矩阵组合在执行前展开, 重试只增加 `attempts`, 不增加计划实例.

每个真实尝试有唯一 `executionId`, `attemptId` 在同一 `(runId, instanceId)` 内按尝试顺序区分. 未启动项使用 `attempts: []`/`finalExecutionId: null`, 不伪造尝试 ID 或执行时间; 已启动项如实记录停止位置. `finalExecutionId` 仅引用按缺陷闭环和基线规则选定的本次有效尝试, 不能自动取最后一次成功. 跨运行复测另建 runId 并保留来源引用.

范围/环境/汇总报告可为 run 级制品, 不强制关联不存在的 executionId. 共享报告须可定位每个关联实例及尝试. 数量按第 1.4 节逐项复算, 历史失败/当前有效结果/唯一缺陷/尝试次数分别统计, 不删除失败或重复计缺陷.

证据文件必须实际存在/非空/可读/格式有效, 制品引用可由交接方访问. 哈希只检测归档后变化, 不能单独证明真实执行, 必须与运行器/时间/版本/业务步骤互相核对.

### 9.5 存储/安全与保留

- 测试/稳定 Fixture/规则/矩阵/核准视觉基线纳入版本管理; 报告及索引应入版本管理或受控制品系统.
- 大型 Trace/视频/导出/日志放专用目录或制品库, 不默认全入 Git. 明确忽略规则/上传/保留配置, Git 外证据仍须交付/可访问/受控保留.
- 优先合成数据; 排查请求/响应/截图/Trace/导出/配置/日志中的密码/Token/Cookie/连接串/真实敏感信息.
- 保留角色与身份别名, 不存可登录秘密. 必要敏感证据限授权存储, 公开报告仅引用可分享的脱敏版本.
- 脱敏须保留断言字段及关联能力, 不得隐藏错误; 哈希针对实际交付版本计算.
- 至少保留到人工复验/上线/约定回溯期结束. 期限未约定时, AI 禁止自行清理历史验收证据.
- 删除测试数据前先归档证据; 删除历史证据遵循确认的保留策略, 不得为省磁盘清除失败记录.

### 9.6 统一模板与格式校验

项目必须提供与第 9.4 节对应的 JSON Schema/记录模板/运行器转换器, 按第 9.3 节置于 scripts/testing/ 下或已登记的等价位置, 统一使用 UTF-8 JSON 或 JSONL. `schemaRef` 必须指向可访问的格式定义. 模板和工具源码不得以运行证据目录作为唯一保存位置. 模板和示例不属于运行证据; 生成记录须来自本次计划/采集/观察, 不得复制示例填充结果.

格式定义至少约束: 必填字段/类型/枚举/带时区时间/引用格式, 以及不适用原因与确认依据/无尝试时空值/真实尝试执行身份等条件必填关系. ID 使用非空字符串, `attemptId` 使用正整数, 计数使用非负整数, 数组和空值按 Schema 明确定义. JSONL 每行一个完整对象, 未识别状态或格式错误禁止自动转换成通过.

经确认不适用的条目, 实现定位/运行预期等无实际意义的字段可按 Schema 为空, 原因和确认依据不可为空; 不得为补字段虚构实现/预期/运行记录.

`stage` 统一采用 `PREPARATION`/`DEVELOPMENT`/`MODULE`/`ACCEPTANCE`/`HANDOFF`, 分别对应编码前/开发自测/模块验收/全量收口/人工复验交接; `requiredStages` 使用同一枚举. 常规后置专项只在其必测阶段进入执行清单, 按第 2.1 节处理.

以下为关联关系模板, `<...>` 须替换为真实计划信息, 其余第 9.4 节必填字段必须补齐后才能交付. 第一个对象用于 `scope/cases.jsonl`, 第二个用于 `cases.jsonl`. 模板表示计划中的当前阶段用例尚未执行, 不代表测试通过:

```json
{
  "scopeId": "<scopeId>", "caseId": "<caseId>", "instanceId": "<instanceId>",
  "applicability": "APPLICABLE", "requiredStages": ["MODULE", "ACCEPTANCE"],
  "applicabilityReason": "<适用原因>", "confirmationRef": "<确认依据引用>",
  "evidenceRequirements": ["<本用例所需证据类别>"]
}
```

```json
{
  "runId": "<runId>", "instanceId": "<instanceId>",
  "scopeRef": "<冻结范围中该实例的引用>",
  "status": "NOT_RUN", "evidenceStatus": "INCOMPLETE",
  "finalExecutionId": null, "attempts": [], "artifactIds": []
}
```

实际尝试按第 9.4 节填写到 `attempts`; 当前结果/证据完整性/有效尝试引用必须在执行及审查后生成. 无错误时也按第 9.2 节生成数量为 0 的采集记录, 不用空数组或缺文件代替已完成采集.

### 9.7 运行器状态映射

转换器必须保留原始报告及原状态, 按实际行为映射, 不得仅翻译运行器的汇总标签:

| 原始情况 | 规范记录与门禁处理 |
| --- | --- |
| 实际执行且预定断言全通过 | 该尝试记 `PASS`, 证据另行审计; 当前有效结果按基线和缺陷闭环选定 |
| 断言失败/非预期业务错误 | 该尝试记 `FAIL`, 保留诊断并关联原因或缺陷 |
| 前置故障导致无法验证 | 记 `BLOCKED`, 写明原因/依赖/解除条件; 未启动则无尝试记录 |
| 必测项被 skip/禁用/过滤/漏发现 | 记 `NOT_RUN`; 有可核查阻塞依据时记 `BLOCKED`, 不得转成不适用 |
| 失败后自动重试成功或 flaky | 保留全部尝试, 不直接汇总为 `PASS`; 原因未闭环时保留失败结论并阻止通过, 有效复测按第 10/11 节判定 |
| 已知缺陷的预期失败标记 | 依据真实断言记录失败或未执行, 不得当作负向业务用例通过; 正确拒绝非法输入仍按第 8.1 节判断 |
| 超时/中止/进程崩溃 | 保留已完成结果和真实尝试; 实际违反预期记 `FAIL`, 受阻未完成记 `BLOCKED`, 未开始记 `NOT_RUN` |
| 未识别状态/解析失败 | 保留原始内容, 记录转换故障并阻止自动通过; 不能证明已执行的项记 `NOT_RUN` |

## 10. 自动门禁与证据审计

必须建立机器可执行门禁. 未具备的检查器/采集脚本列为待落实项, 全量收口前补齐; 本规范或人工自述不能冒充已运行门禁.

统一工具链应从运行器原始报告生成第 9 节记录, 再由检查器校验; 禁止由总结文字反向生成通过记录. 工具接口必须记录输入路径/命令/配置/自身身份及 invocationId, 汇总遵守第 9.3 节单一写入规则, 满足以下约定:

| 环节 | 输入 | 必须输出或验证 |
| --- | --- | --- |
| 采集与转换 | 冻结范围/阶段/baselineId/构建记录/原始报告与制品 | manifest/cases/artifacts, 保留原报告和每次尝试, 按第 9.7 节转换 |
| 格式与关联检查 | 对应 JSON Schema 及全部机器记录 | 类型/条件必填/枚举/实例与尝试唯一性/引用有效性; Schema 校验不能代替跨文件核对 |
| 范围与结果核对 | 冻结阶段清单/各 run 计划及实际发现清单/逐项结果/尝试历史 | 本批次计划内缺结果记 NOT_RUN 或有依据的 BLOCKED; 最终按完整阶段清单跨 run 去重核对, 无遗漏/多计/越阶段排除 |
| 证据与验收检查 | 制品/构建与基线身份/缺陷和复测/独立审查记录 | 执行 G-01 至 G-10, 输出 gate-result.json 及人可读问题清单 |
| 报告与索引生成 | 已校验的机器记录/门禁结果/原始观察引用 | 生成同一运行目录内的 report.md 及证据索引, 已登记的同源视图按需更新, 不改写原始结果 |

自动通过须所有适用门禁通过; 经确认不适用的门禁记录 `NOT_APPLICABLE` 及依据, 不伪装成 `PASS`. 工具退出码统一为 `0` = 适用门禁全部通过, `1` = 验收条件未满足, `2` = 工具/输入/配置故障; 外层 CI 必须将非零视为失败. 未执行的检查不写通过结果, 工具崩溃保留日志及部分记录, 不用成功空文件替代.

分批执行时, 最终检查器必须接收同一冻结基线下全部纳入的 runIds, 按完整阶段清单为每个 instanceId 列出有效结果/来源 runId/执行引用, 跨运行重复实例只计一次, 缺项不得通过. 子批次通过只能说明该批次结果; 尚待其他批次执行的项不能标为不适用, 阶段门禁仍须返回未满足条件. 批次运行器的成功退出码不等于阶段门禁通过. 最终门禁输出保存在本次明确指定的验收运行目录, 不覆盖既有归档.

检查器本身必须用固定样例验证: 合法记录可通过格式与关联检查, 缺证据/重复实例/漏用例/混用基线/重试掩盖失败/不适用无依据均能被拒绝. 示例/字段表/检查器存在均不等于已执行门禁, 仍须保留本次检查记录.

| 门禁 ID | 必查内容 | 不满足时 |
| --- | --- | --- |
| G-01 范围 | 完整范围已确认, 流程/规则/实例映射完整, 适用性及阶段有依据, 无静默移除 | 不得宣称完整覆盖 |
| G-02 测试发现 | 预期套件/用例实际发现, 数量与范围相符 | 零用例/漏发现不得通过 |
| G-03 执行完整 | 本阶段必测实例有逐项结果, 构建前置条件满足, 无未说明过滤/禁用/skip/ignore/only/focus | 构建失败阻止依赖测试, 遗漏记 BLOCKED 或 NOT_RUN, 阻止阶段通过 |
| G-04 结果一致 | 原始运行器状态/退出码/逐实例结果/全部尝试/汇总可对账 | 调查差异, 不得择取有利结果或按重试虚增覆盖 |
| G-05 证据完整 | 证据齐全, 路径/大小/格式/哈希/用例关联有效 | INCOMPLETE, 不计验收通过 |
| G-06 版本一致 | 代码/测试/依赖/工作区/产物/配置/数据集/环境符合可核查的 baselineId | 旧基线结果不得补齐最终基线执行缺口 |
| G-07 缺陷闭环 | 失败有缺陷或原因, 关闭有复测回归, 无未解释偶发失败 | 阻止受影响验收, 全量按第 11 节 |
| G-08 视觉基准 | 适用页面有布局/视觉/截图检查, 基线更新有依据 | 不得声称界面通过 |
| G-09 真实链路 | 核心链经真实接口及目标部署, 替身/领域直调边界已揭示 | 不得声称真实全链通过 |
| G-10 最终专项 | 全量并发/性能/稳定性/部署/适用升级恢复有有效结论 | 全量不通过 |

skip/only 等扫描须判断是否影响实际运行, 文档或工具源码同名文本不机械判失败. 必测项被跳过/过滤/禁用必须反映在结果与门禁中.

以第 1.4 节冻结清单中的唯一实例为分母, 重试不增加覆盖数. 退出成功但零用例/只跑部分阶段或冒烟/过滤失败项均不构成全量通过.

保留原失败及全部尝试. 仅原因查明/必要修复完成/有效复测满足第 11 节基线时, 可采用复测作为当前结论; 未解释偶发失败仍阻止完全通过.

机器门禁检查结构/结果/一致性, 独立验收 AI 还必须审查业务预期/断言质量/实际证据/范围合理性.

## 11. 阶段完成与全量收口标准

### 11.1 开发和模块阶段

阶段通过须同时满足:

1. 影响范围及必测清单明确.
2. 必测项通过且证据完整, 相关缺陷完成复测.
3. 关联规则/接口/UI/数据回归完成, 适用构建及静态检查通过.
4. 后置并发/性能等必测项已登记为全量收口范围.
5. 报告明确实际覆盖/未覆盖/项目已知其他问题, 不扩大结论.

其他范围有问题时可报告 "本次变更/本模块验证通过", 不得称项目验收通过. 本阶段有 `FAIL`/`BLOCKED`/`NOT_RUN` 或证据不完整时, 只能报告部分完成及缺口.

### 11.2 全量收口准备

独立全量收口前必须:

- 冻结交付范围/业务口径/用例/支持矩阵/专项标准.
- 指定独立验收 AI, 提供规则/源码/测试/缺陷/环境资料.
- 冻结候选源码/实际依赖/测试/产物/部署配置/数据集版本, 生成可核查的 `baselineId`.
- 在可重复环境按锁定依赖构建/部署/初始化, 验证目标入口可用.
- 准备自动采集/门禁/数据隔离/清理/恢复方案.

预期或专项阈值未确认/依赖缺失时可执行不受影响部分, 不得臆造受阻预期或给出全量完全通过.

### 11.3 并发/性能与持续稳定性

全量收口必须执行适用专项, 用户明确指定时可提前. 执行前列明场景/工具/环境规格/数据量/持续时间/采集方式/通过阈值.

| 专项 | 至少考虑的适用场景 | 通过依据 |
| --- | --- | --- |
| 并发正确性 | 同对象同时操作/并行提交审核执行/资源竞争/同时修改/重复副作用 | 已确认一致性与冲突规则, 无丢更新/非法状态/越限/不应发生的重复写入 |
| 接口/页面性能 | 核心查询/保存/统计/导入导出/页面可用时间, 典型及目标规模数据 | 预先确认的响应分位数/错误率/吞吐或处理时长 |
| 持续稳定性 | 代表性负载/后台任务反复运行/连接和资源释放/异常恢复 | 预先确认的时长/资源趋势/错误/恢复目标, 无未解释持续恶化 |

无适用于所有项目的默认合格数字. 用户/业务负责人应按目标规模确认阈值; AI 可提出并论证建议, 不得按测试结果反设合格线.

如实记录环境瓶颈/目标规模未建立/测量失真. 低负载开发机冒烟不得用于推断目标部署性能达标.

### 11.4 构建/部署/升级与恢复

全量必须验证生产配置构建及目标部署或真实宿主接入, 覆盖适用的路由/登录认证/接口/静态资源/后台任务, 不适用项按第 1.4 节登记.

持久化系统须在隔离环境验证必要的重启/数据保留/备份恢复/版本回退. 结构/数据/配置升级须从实际支持旧版验证, 核对记录/关联/金额/状态/统计.

恢复及回退须核对恢复数据和关键业务冒烟, 不只看退出码. 无法直接回退须有已验证替代恢复方案并明确交接. 这些验证不授权操作生产或上线.

### 11.5 完全通过的硬性条件

以下必须全部满足:

1. 已确认完整交付范围的必测用例 **100% 实际执行且 PASS**, 规定证据全部 **COMPLETE**.
2. 当前有效结果 **FAIL = 0/BLOCKED = 0/NOT_RUN = 0**, 无未解释跳过/遗漏/不稳定项.
3. **未解决 BLOCKER = 0/MAJOR = 0/MINOR = 0**; 保留历史失败, 已关闭缺陷有有效复测及回归.
4. 业务规则/计算口径/验收标准无影响交付结论的待确认项.
5. 第 1.4 节确认适用的三层验证/关键真实 E2E/权限/异常/数据核对/布局/视觉检查完成, 无 UI 的交付物完成对应真实服务/宿主验证.
6. 构建/静态检查/契约/真实部署/适用升级恢复通过.
7. 适用并发/性能/持续稳定性达到预先确认标准.
8. 自动门禁通过, 独立验收 AI 完成范围/预期/实际证据审查.
9. 有效证据对应最终冻结候选基线, 人工复验资料完整可访问.

最终有效结果须按缺陷闭环及版本要求产生, 不得删除历史失败或只筛成功尝试. 可分批次/浏览器/场景执行, 但须属于同一冻结候选基线及预先声明的环境矩阵. **禁止拼接不同代码/产物版本的局部通过来宣称单一版本全量通过.**

### 11.6 变更/例外与人工复验

影响应用/预期/测试判断/环境的变更使相关旧结论失效. 开发修复阶段可先执行问题复测及影响范围回归; 宣称全量收口完全通过前, 必须由独立验收 AI 在最终冻结候选基线上重新执行完整适用必测清单及全部适用门禁. 旧基线下未受影响的通过结果也只作参考, 不得用于补齐最终基线的执行缺口. 可按同一基线分批执行, 不要求全部测试处于同一进程或单次运行.

用户明确批准缩减范围或暂缓缺陷时, 保留原范围/变更依据/风险/未完成项/批准记录. 仅可称 "条件通过" 或 "按调整范围完成", 不得冒充原范围完全通过, 也不自动触发原定人工复验或上线流程.

AI 全量完全通过后, 以同一候选产物及受控配置交人工复验. 人工发现缺陷须返回修复及针对性复测, 再由独立验收 AI 按本节要求在最终基线完成完整验收后重新交人工复验.

人工通过后使用已验收产物上线. 重建仅在能证明冻结基线与产物一致时可沿用结论; 更换依赖/配置或无法证明一致时, 须重新冻结候选基线并完成本节规定的独立完整验收及人工复验. AI 完全通过不等于人工通过或自动发布授权.

## 12. 必交付报告与执行清单

### 12.1 每次测试报告

报告按第 9.3 节保存为本次运行证据包中的 report.md, 状态和统计同源生成, 观察与解释注明出处. 必须包含:

1. 任务/阶段/runId/起止时间/执行者及独立验收者.
2. 代码/测试/依赖/工作区差异/构建产物/环境身份.
3. 本次范围/规则来源/范围变更/适用性及确认依据/后置项/冻结实例分母.
4. 命令/数据/角色/真实及替身依赖边界.
5. 逐项结果与汇总, 分别统计计划实例/证据完整性/唯一缺陷/历史失败/执行尝试, 不以重试增加覆盖数.
6. 三层验证/视觉/数据/本阶段适用专项结果.
7. 缺陷/阻塞/未执行/原因/修复和复测入口.
8. 自动门禁及独立审查结论, Schema/转换器/检查器身份与执行入口.
9. 人工复验账号获取方式/页面与流程入口/数据标识/证据入口, 不写密码.
10. 明确结论: "本范围通过"/"未通过或部分完成"/"全量收口完全通过"/经批准的条件结论.

不得以 "基本没问题"/"应该通过"/"代码看起来正常" 代替逐项结果. 未执行检查必须明示.

## 13. 各项目测试入口与落实

执行前必须只读核查当次仓库, 登记下列入口及差距. 不沿用其他项目的路径/脚本名/技术版本/默认配置来推断当前能力.

| 核查对象 | 必须确认 |
| --- | --- |
| 阅读与续接入口 | 根 README 可定位规范/功能文档/测试编写指南, 模块文档或脚本可定位执行入口, 运行包及适用 handoff.md 可定位本次范围/基线/证据/阻塞, 无独立维护的冲突运行结论 |
| 前端脚本与测试配置 | 实际构建/测试/覆盖率入口和发现范围; 部分阶段/结构测试/冒烟不得代替完整范围 |
| 浏览器配置 | worker/重试/浏览器/视口, 成功与失败的 Trace/截图/错误采集/逐项索引及输出清理范围是否满足本规范 |
| 后端测试项目及辅助代码 | 规则/接口/ApiFlow/数据断言/机器报告, 进程内边界及是否绕过真实登录/授权/公共操作 |
| Geex 框架及扩展依赖 | 实际引用版本或源码/本地依赖构建/前后端契约/宿主接入; 库内测试不代替项目真实链路 |
| 现行业务流程文档 | 完整入口/关联/计算/疑点转换为有确认依据的覆盖矩阵, 疑点以运行验证或业务确认闭环 |
| 证据与门禁工具 | Schema/模板/转换器/检查器入口及适用阶段, 原始报告到统一记录的映射, 独立输出及单一汇总规则, 固定正反样例及本次检查输出 |

核实构建脚本是否使用生产配置, 全量收口须选择实际生产构建入口. 冻结验收使用不修改文件的静态检查; 若发生自动修复, 记录变更并重新确定基线.

测试名称或辅助函数存在不证明链路已覆盖. 覆盖矩阵/采集/机器记录/门禁/必要回归的缺口, 在落实并实际验证前保持待办. **不得因规范落盘而宣称测试体系完成或项目验收通过.**
